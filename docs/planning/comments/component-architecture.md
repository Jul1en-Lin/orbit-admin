# 确定组件边界、目录组织与主题复用约定：讨论记录

## Resolution

用户确认以下最终结论，并同意本会话归档关闭[确定组件边界、目录组织与主题复用约定](../issues/08-component-architecture.md)。本次仅确定约定，不实现正式组件。用户要求暂停后续页面验收讨论，下次继续。

### 目录与复用

- 按业务聚合代码：管理端账号、字典、参数分别组织页面、专属组件、接口与类型；布局、认证、通用基础能力独立。
- 业务模块通过明确的对外入口复用，不跨模块引用页面或内部组件。
- 只有确实被多个业务使用的能力才进入共享目录，不预建大而全的工具层。

### 组件封装

- 表格、表单、输入框、下拉框和弹窗直接使用 Element Plus。
- 自写统一布局、页面框架、标题区等确实重复的结构；重复业务行为出现后再提取组件。
- 首版不建设万能表格、配置式表单，不给每个基础控件增加纯转发封装。

### 主题与样式

- 集中维护品牌颜色、字体、间距和边框等主题变量，映射到 Element Plus 主题。
- 全局主题负责统一视觉及下拉、弹窗等浮层；页面局部样式负责本页面布局。
- 避免各页面分别覆盖组件库内部样式，不建设多主题切换。

### 状态归属

- 首版不做跨页面列表缓存：筛选和分页保留在页面内部，重新进入时恢复默认。
- 未提交表单不跨页面保存。
- Pinia 仅承载确实需要跨页面共享的状态，例如当前登录会话，不集中存放所有页面数据。

### 请求与错误处理

- 统一请求层处理认证头、响应解包和统一 401。
- 业务接口层定义接口调用、请求与返回类型及必要的数据转换。
- 页面管理加载状态、成功反馈和业务失败交互。
- 同一次失败只提示一次，避免请求层与页面重复弹出消息。

### 测试组织

- 用户明确选择集中存放测试，不采用紧邻源码的方案。
- 测试统一放在根目录 `tests/`，按源码业务结构对应组织，使用 `*.test.ts`；共用测试初始化也集中在该目录。
- 测试工具、覆盖边界与质量门槛继续遵循[首版工程工具与质量门槛](engineering-baseline.md)。
