# 确定前端独立部署与环境配置边界：讨论记录

## 已确认的方向

用户确认以下部署方案；下述内容不是部署验证通过的声明。

- 云服务器目前尚未部署后端。前端完成后，前后端安排在同一次上线中，但分别构建与部署，不合并成一个应用包。
- 同一台云服务器使用 Nginx 作为统一入口：托管前端构建后的静态文件，API 转发到现有后端网关，不绕过网关直连业务服务。不要求生产服务器持续运行 Node 来提供前端页面。
- 前端在站点根路径部署，采用 Router history 模式。页面路由刷新回退至 index.html；API 和缺失静态资源不得错误回退为页面。
- 浏览器使用同源 `/api` 入口。本地使用 Vite 开发代理，上线后使用 Nginx 代理；开发代理不随构建产物进入生产。
- `/api` 是前端侧约定，不代表后端已有此前缀。剥离、替换及实际转发路径须根据网关配置核实后确定。
- 接受构建时配置，不建设额外的运行时配置加载机制。后端目标地址配置在开发代理或 Nginx；浏览器可见配置均视为公开信息，不放服务端秘密。
- 开发阶段先在本机运行后端，完成真实接口联调；上云后再验收部署链路，不等上线时才首次联调。
- 上线部署验证留到上线准备阶段，未完成时明确标记“未验收”。

## 事实与待核实项

只读核查后端仓库的结果与[认证源码核查](../assets/auth-contract.md)一致：网关路由、重写及登录白名单依赖外部 Nacos 配置；仓库无法确定真实 API 外部前缀和网关端口，也未验证运行时 CORS 或 OPTIONS 行为。service-local 路径不是已确认的浏览器 API 地址。

实现与联调阶段通过[提供本地联调所需的网关配置与访问条件](../issues/09-local-gateway-access.md)取得必要的非秘密信息，再确定开发代理及生产转发规则。云服务器域名、HTTPS 与部署链路的具体验收仍待后续核实，不在本次讨论中视为已完成。
